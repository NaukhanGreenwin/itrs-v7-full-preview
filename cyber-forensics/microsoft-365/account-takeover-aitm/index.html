Microsoft 365 forensics

Account Takeover and AiTM Token Theft Investigation

When MFA was on and the account was still taken, the answer is usually a stolen session token.

24/7 (289) 582-9930Report an incident

Adversary-in-the-middle (AiTM) phishing kits sit between the user and the real Microsoft sign-in page, so the user completes MFA and the attacker keeps the session cookie. We trace the phishing link, the stolen session and every place it was replayed, for organisations across Toronto and the GTA.

What we do

What the investigation covers

  • Phishing path

    The email, link and proxy domain that captured the sign-in.

  • Session replay

    Matching session IDs used from a new IP, device or browser.

  • Persistence

    New MFA methods, app passwords or devices the attacker registered.

  • Hardening

    Phishing-resistant MFA, token protection and conditional access gaps.

Questions

Frequently asked questions

How can an account be taken over when MFA is enabled?

In an AiTM attack the user signs in and approves MFA on a proxy page that relays to Microsoft. The proxy keeps the session cookie, and the attacker replays it, so the sign-in looks already authenticated.

Does a password reset remove the attacker?

Not on its own. You also need to revoke refresh tokens and sessions, remove MFA methods and devices the attacker registered, and check for inbox rules and app consents they left behind.

What evidence shows a token was stolen?

Entra ID sign-in logs record session IDs, IP addresses, device details and whether MFA was satisfied by a claim in the token. One session ID appearing from two unrelated locations minutes apart is a strong sign of token replay.

How do we stop it happening again?

Phishing-resistant methods such as FIDO2 security keys or passkeys cannot be relayed by a proxy page. Conditional access that requires a compliant device, and token protection where licensed, make a stolen cookie much harder to use.
